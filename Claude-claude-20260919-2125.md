## First, the hard truth about "all books"

There is no route — official or otherwise — that hands you a complete enumeration of amazon.in's book catalogue. Every option is a way of _approximating_ completeness, and they fail differently:

- **Category browsing** caps out. Amazon's own search/browse pages stop at ~7 pages (~400 results) per query, no matter how many matches exist. So you can't walk a browse node to exhaustion.
- **Keepa's Product Finder** queries Keepa's database, not Amazon's — Keepa's docs say plainly that it may not find every matching product on Amazon, and that running the same query twice can return different sets as products shift. A single query also returns at most 10,000 ASINs via paging.
- **Official APIs** are deliberately not bulk tools (more below).

So the real design question is: what do you slice the catalogue into, so that no slice exceeds the per-query cap?

## Keepa on amazon.in — it does work

Domain ID `10` is `in`, so amazon.in is supported. Product Finder is the endpoint you want, and it has the filters for exactly your exclusion:

```json
{
  "rootCategory": [976390031],
  "productType": 0,
  "binding": ["✜Kindle Edition", "✜Audible Audiobook", "✜Audio CD", "✜MP3 CD"],
  "perPage": 10000,
  "page": 0
}
```

Books on amazon.in is browse node `976390031` (verify with Keepa's category search endpoint before hardcoding it — node IDs do move). The filters doing the work:

- `productType` distinguishes STANDARD (`0`), DOWNLOADABLE (`1`), EBOOK (`2`) and VARIATION_PARENT (`5`) — setting it to `0` kills Kindle and downloadables in one move.
- String filters can be inverted with the `✜` prefix, so you can knock out audio bindings explicitly. Alternatively go positive: `"binding": ["Paperback","Hardcover","Mass Market Paperback","Board book","Spiral-bound","Library Binding"]`.
- `numberOfPages` is a filter — requiring `numberOfPages_gte: 1` is a decent extra sanity check for "is this a physical book."

**Two gotchas worth knowing before you burn tokens:**

1. If you don't set the `lastUpdate` filter, the query is silently limited to products Keepa updated in the last 6 months. Set it explicitly or you'll quietly lose the long tail of dormant listings — which, for books, is most of them.
2. Cost is 10 tokens per request plus 1 token per 100 ASINs returned, and requests execute even when your balance goes negative. A full-catalogue crawl will run your balance deep into the red if you're careless.

### The bucketing strategy

Since no single query can exceed 10k results, you partition recursively. Every response includes `totalResults`, the estimated count of all matched products — that's your split signal:

1. Query Books root + physical-only filters. Read `totalResults`. That single cheap call tells you the size of the job before you commit to anything.
2. If >10,000, split on a dimension and re-check each child. Good split axes, in rough order of usefulness: `categories_include` (the 28 child nodes under Books, then their children), then `current_NEW_gte/lte` price bands in paise, then `publicationDate` ranges, then `numberOfPages` bands, then `languages`, then `publisher`.
3. Recurse until every leaf is under 10k, then page through each.
4. Feed the collected ASINs to the Product request (1 token/ASIN) for actual metadata.

Price bands are the workhorse — they're continuous, so you can binary-split them indefinitely, unlike categories which bottom out.

## Alternatives

**The official route changed in 2026 and is now worse for you.** PA-API stopped accepting new customers and was deprecated; it was deprecated April 30, 2026 with the endpoint shut down May 15, 2026, replaced by the Creators API. It won't help anyway: SearchItems returns up to 10 items per call and GetItems accepts 10 IDs per call, and new credentials start at 1 request/second with a daily cap of 8,640 requests, scaling only with your Associates account's qualified sales. ## The approach that actually gets you close to complete

For books specifically, there's a trick the general-purpose tools miss: **for most print books, the ASIN _is_ the ISBN-10.** That inverts the whole problem. Instead of asking Amazon "what books do you have," you bring your own list of every book that exists and ask Amazon "do you carry this one?"

Seed sources:

- **Open Library dumps** — free, CC0, refreshed monthly. Over 20 million editions. The editions file is about 45GB uncompressed and you'll want ~250GB free to import it; DuckDB handles it without a Postgres import if you'd rather.
- **ISBNdb** — paid, but broader commercial coverage and cleaner records.
- **Nielsen BookData India / Indian Registrar of ISBNs** — worth chasing if India-published titles are the priority, since Open Library's Indian-publisher coverage is patchy.

Then: filter the seed list to physical formats, derive ISBN-10s, and resolve each against amazon.in. Keepa's Product request accepts UPC, EAN and ISBN-13 codes alongside ASINs, though if the code isn't in Keepa's database nothing is returned — so a hybrid works well: ISBN list → Keepa bulk lookup → fall back to a scraper API for the misses.

**In practice I'd run both.** Keepa Product Finder bucketing gives you what Amazon India actually stocks including ASIN-only books with no ISBN. The ISBN seed list catches the long tail Keepa never tracked. Deduplicate on ASIN.

## One caveat

Amazon's ToS prohibits automated access to its pages, and using a third-party scraper shifts that exposure rather than removing it. Keepa and the official APIs are contractually cleaner ground. Worth a thought depending on whether this is a personal project or something you're building a business on.

## Three things that will blow up your budget if you don't plan for them

**Keepa's constraint is rate, not money.** The bucket holds at most `rate × 60` tokens, so you can't stockpile a month's allowance and burst through it. On the €2,499 Business plan you're capped at 120,000 tokens in any single burst. Also worth knowing: users have reported a separate daily quota designed to deter heavy extraction, described as roughly 24,000 ASINs/day recovering at 5%/hour. Test this against your actual plan before you commit to a multi-month crawl.

**Discovery is a separate line item on scraper APIs.** With Oxylabs or Bright Data, finding 200M ASINs costs money on top of fetching them. A search results page returns ~48 products for one billable result, so discovery adds roughly 20–30% — but only if you can enumerate at all, and Amazon's ~400-result pagination ceiling means you often can't.

**None of these prices include your own costs.** Storage for 200M records, the compute to process them, and the engineering time to build and babysit a crawl that runs for weeks. At full-catalogue scale that's frequently larger than the API bill.

One India-specific note: these are all foreign SaaS vendors, so IGST under reverse charge will likely apply on top of the listed prices. Worth checking with whoever handles your compliance rather than assuming the sticker price is final.

Here's the whole thing in plain terms.

## The one idea that makes it click

Keepa is not Amazon. Keepa is a **copy of Amazon's catalogue** that Keepa built and keeps updated. When you use their API, you're searching their copy, not Amazon's live site.

This is good news and bad news. Good, because a database can be filtered and sorted in ways Amazon's website will never let you. Bad, because if a book isn't in Keepa's copy, no amount of clever querying will find it.

The second idea: **there is no "give me all books" button.** What you actually do is ask a lot of narrow questions and glue the answers together. That's the whole job.

## The process, step by step

**Step 1 — Get the map.**

Before you can ask narrow questions, you need to know what the categories are. Keepa has a lookup that returns the category tree for amazon.in — Books at the top, then its children (Fiction, Children's, Textbooks, Business, and so on), then _their_ children, going several levels deep. You pull this once and save it. It costs almost nothing. Now you have a list of maybe a few hundred category nodes.

**Step 2 — Harvest ASIN lists.**

You now go and collect ASINs. Keepa gives you two different tools for this, and you should use both, because each one misses things the other catches.

_Tool one: Best Sellers lists._ You hand Keepa a category node and it hands back a ranked list of ASINs in it. This is absurdly cheap — 50 tokens flat, and a top-level category list can hold up to 500,000 ASINs. So you loop through every node in your map from Step 1, asking for each one's list. A few hundred calls, a few thousand tokens, and you've got millions of ASINs.

The catch: these lists only contain products that _have a sales rank_. A book that has never sold a copy on amazon.in has no rank, so it simply isn't there. That's a real hole, and for books it's a big one — the long tail of obscure titles is exactly what gets excluded.

_Tool two: Product Finder._ This is the filtered search. You say "books, physical only, published between 2010 and 2012, priced ₹200–400" and it returns matching ASINs. It doesn't care about sales rank, so it catches the books the Best Sellers lists missed.

The catch here: one query returns at most 10,000 ASINs, no matter how many actually match. So you can't just ask for "all books" — you'd get 10,000 and silently lose the rest.

**Step 3 — Slice until the buckets fit.**

This is the only genuinely fiddly part, and it's what makes Product Finder work despite the 10,000 cap.

Every response tells you `totalResults` — how many products matched in total, even if it only returned 10,000 of them. So you use that as a signal:

Ask for all books. It says 4 million matched. Too big. So you split it — books under ₹500, and books over ₹500. Ask again. Under ₹500 says 2.5 million. Still too big. Split again: ₹0–250 and ₹250–500. Keep splitting until each slice reports under 10,000. _Then_ you actually pull that slice's ASINs.

It's the same move as looking up a word in a dictionary by repeatedly halving. You can split on price, publication date, page count, language, publisher — anything numeric works best because you can always halve it again.

**Step 4 — Pile everything together and remove duplicates.**

The two tools will return heavily overlapping lists, and your category slices will overlap too (a book sitting in three subcategories shows up three times). Dedupe on ASIN. Now you have one clean list.

**Step 5 — Go get the actual books.**

Everything so far gave you nothing but ASINs — bare identifiers, no titles, no prices. Now you make product requests, 100 ASINs at a time, 1 token each. _This is where nearly all your money goes._ Steps 1–4 might cost a few thousand tokens; Step 5 costs one token per book, so a few million books is a few million tokens.

**Step 6 — Filter properly.**

You filtered at query time, but do it again on the real data. Check that each record has a physical binding, a page count, an ISBN where expected. Drop anything that slipped through as a Kindle edition or an audiobook.

## What you'll still miss, honestly

Books Keepa never indexed. Books with no sales rank _and_ missing the attributes you filtered on. Brand-new listings Keepa hasn't picked up yet. Books whose category assignment on Amazon is wrong, so they don't appear under Books at all.

There's no way to know how many you missed, because there's nothing to compare against. That's why the ISBN approach I mentioned earlier is a useful companion — bringing your own list of books that exist in the world and checking them against Amazon gives you a second, independent angle on the same catalogue.

**keepa_book_categories.py — crawl the full Books category tree on amazon.in**

```python
#!/usr/bin/env python3
"""
Crawl the complete Books category tree from the Keepa API for a given Amazon locale.

Walks breadth-first from the Books root node, batching 10 category IDs per request
(1 token per request regardless of batch size), and writes out:

    books_categories.json  - full catId -> category object map
    books_categories.csv   - flat table: id, name, depth, parent, children, productCount, path
    (stdout)               - node counts by depth, leaf count, token spend

Usage:
    export KEEPA_KEY=your_key_here
    python keepa_book_categories.py                    # amazon.in, auto-detect Books root
    python keepa_book_categories.py --domain 1         # amazon.com
    python keepa_book_categories.py --root 976390031   # skip auto-detect
    python keepa_book_categories.py --resume           # continue an interrupted crawl
    python keepa_book_categories.py --max-depth 3      # stop early (useful for a dry run)

Token cost: roughly ceil(nodes / 10) + 1. A tree of 5,000 nodes costs ~500 tokens.
"""

import argparse
import csv
import json
import os
import sys
import time
from collections import deque, defaultdict

import requests

ENDPOINT = "https://api.keepa.com/category"
BATCH_SIZE = 10           # Keepa accepts up to 10 category ids per request, still 1 token
CHECKPOINT = ".keepa_categories.checkpoint.json"

DOMAINS = {
    1: "com", 2: "co.uk", 3: "de", 4: "fr", 5: "co.jp",
    6: "ca", 8: "it", 9: "es", 10: "in", 11: "com.mx",
}

class KeepaCategoryClient:
    """Thin wrapper over /category with token-bucket awareness and retries."""

    def __init__(self, key, domain, min_tokens=5, verbose=True):
        self.key = key
        self.domain = domain
        self.min_tokens = min_tokens
        self.verbose = verbose
        self.session = requests.Session()
        self.requests_made = 0
        self.tokens_spent = 0
        self.tokens_left = None

    def _log(self, msg):
        if self.verbose:
            print(msg, file=sys.stderr, flush=True)

    def lookup(self, cat_ids, parents=0, max_retries=5):
        """Look up up to 10 category ids. Returns the `categories` map (str id -> object)."""
        params = {
            "key": self.key,
            "domain": self.domain,
            "category": ",".join(str(c) for c in cat_ids),
            "parents": parents,
        }

        delay = 2.0
        for attempt in range(max_retries):
            try:
                resp = self.session.get(ENDPOINT, params=params, timeout=60)
            except requests.RequestException as exc:
                self._log(f"  network error ({exc}); retrying in {delay:.0f}s")
                time.sleep(delay)
                delay *= 2
                continue

            # Rate limited or server-side hiccup: back off and retry.
            if resp.status_code == 429 or resp.status_code >= 500:
                self._log(f"  HTTP {resp.status_code}; backing off {delay:.0f}s")
                time.sleep(delay)
                delay *= 2
                continue

            if resp.status_code != 200:
                raise RuntimeError(f"HTTP {resp.status_code}: {resp.text[:300]}")

            data = resp.json()

            if "error" in data and data["error"]:
                raise RuntimeError(f"Keepa error: {data['error']}")

            self.requests_made += 1
            self.tokens_spent += data.get("tokensConsumed", 1)
            self.tokens_left = data.get("tokensLeft")

            self._wait_for_tokens(data)
            return data.get("categories") or {}

        raise RuntimeError(f"gave up after {max_retries} retries on {cat_ids}")

    def _wait_for_tokens(self, data):
        """Sleep if the bucket is nearly empty. Keepa tells us when it refills."""
        left = data.get("tokensLeft")
        if left is None or left > self.min_tokens:
            return
        refill_ms = data.get("refillIn") or 60_000
        wait = refill_ms / 1000.0 + 1
        self._log(f"  token bucket low ({left}); sleeping {wait:.0f}s")
        time.sleep(wait)

    def find_root(self, name_match="books"):
        """Pass category=0 to list all root categories, then pick the Books one."""
        roots = self.lookup([0])
        candidates = [
            (int(cid), obj.get("name", ""))
            for cid, obj in roots.items()
            if name_match in (obj.get("name") or "").lower()
        ]
        if not candidates:
            available = sorted(obj.get("name", "?") for obj in roots.values())
            raise RuntimeError(
                f"No root category matching '{name_match}'. Roots found: {available}"
            )
        # Prefer an exact name match over e.g. "Books & Audible" style siblings.
        for cid, nm in candidates:
            if nm.strip().lower() == name_match:
                return cid, nm
        return candidates[0]

def crawl(client, root_id, max_depth=None, resume=False):
    """Breadth-first walk of the category tree. Returns (nodes, depth_of)."""
    nodes = {}          # int catId -> category object
    depth_of = {}       # int catId -> int depth (root = 0)
    queue = deque()

    if resume and os.path.exists(CHECKPOINT):
        with open(CHECKPOINT) as fh:
            state = json.load(fh)
        nodes = {int(k): v for k, v in state["nodes"].items()}
        depth_of = {int(k): v for k, v in state["depth_of"].items()}
        queue = deque((int(c), d) for c, d in state["queue"])
        print(f"Resumed: {len(nodes)} nodes done, {len(queue)} queued", file=sys.stderr)
    else:
        queue.append((root_id, 0))

    while queue:
        # Pull one batch, all from roughly the same depth.
        batch = []
        while queue and len(batch) < BATCH_SIZE:
            cid, depth = queue.popleft()
            if cid in nodes:
                continue
            batch.append((cid, depth))

        if not batch:
            break

        ids = [cid for cid, _ in batch]
        found = client.lookup(ids)

        for cid, depth in batch:
            obj = found.get(str(cid))
            if obj is None:
                # Promotional or withdrawn node; record the gap and move on.
                nodes[cid] = {"catId": cid, "name": None, "_missing": True}
                depth_of[cid] = depth
                continue

            nodes[cid] = obj
            depth_of[cid] = depth

            if max_depth is not None and depth >= max_depth:
                continue

            for child in (obj.get("children") or []):
                child = int(child)
                if child not in nodes:
                    queue.append((child, depth + 1))

        print(
            f"depth ~{batch[0][1]} | done {len(nodes):>6} | queued {len(queue):>6} "
            f"| tokens spent {client.tokens_spent} | left {client.tokens_left}",
            file=sys.stderr, flush=True,
        )

        _checkpoint(nodes, depth_of, queue)

    if os.path.exists(CHECKPOINT):
        os.remove(CHECKPOINT)

    return nodes, depth_of

def _checkpoint(nodes, depth_of, queue):
    tmp = CHECKPOINT + ".tmp"
    with open(tmp, "w") as fh:
        json.dump(
            {
                "nodes": {str(k): v for k, v in nodes.items()},
                "depth_of": {str(k): v for k, v in depth_of.items()},
                "queue": [[c, d] for c, d in queue],
            },
            fh,
        )
    os.replace(tmp, CHECKPOINT)

def build_path(cid, nodes, root_id, sep=" > "):
    """Walk parent links up to the root to make a human-readable breadcrumb."""
    parts, seen, cur = [], set(), cid
    while cur and cur not in seen:
        seen.add(cur)
        obj = nodes.get(cur)
        if not obj:
            break
        parts.append(obj.get("name") or f"<{cur}>")
        if cur == root_id:
            break
        cur = int(obj.get("parent") or 0)
    return sep.join(reversed(parts))

def write_outputs(nodes, depth_of, root_id, json_path, csv_path):
    with open(json_path, "w", encoding="utf-8") as fh:
        json.dump({str(k): v for k, v in nodes.items()}, fh, indent=2, ensure_ascii=False)

    rows = []
    for cid, obj in nodes.items():
        children = obj.get("children") or []
        rows.append({
            "catId": cid,
            "name": obj.get("name"),
            "depth": depth_of.get(cid),
            "parent": obj.get("parent"),
            "n_children": len(children),
            "is_leaf": len(children) == 0,
            "productCount": obj.get("productCount"),
            "websiteDisplayGroup": obj.get("websiteDisplayGroup"),
            "path": build_path(cid, nodes, root_id),
        })
    rows.sort(key=lambda r: (r["depth"] if r["depth"] is not None else 99, r["path"] or ""))

    with open(csv_path, "w", newline="", encoding="utf-8") as fh:
        writer = csv.DictWriter(fh, fieldnames=list(rows[0].keys()))
        writer.writeheader()
        writer.writerows(rows)

    return rows
```

## The one that matters

**Your four rank windows can only ever return 10,000 ASINs each, no matter how wide you make them.**

Keepa's paging rule is that `page × perPage` must not exceed 10,000. With `perPage: 10000`, page 0 gives you 10,000 and page 1 is instantly over the limit — which is exactly the "depth limit" your `depthError` branch is catching. It isn't a quirk to work around; it's the documented ceiling.

So `rank 1-50k` contains ~50,000 books and you will retrieve 10,000 of them. Same for every other window. Your sampling test still works fine, but as a discovery strategy it silently caps at 40,000 books total.

The fix is the recursive split: **a slice is only harvestable if its `totalResults` is already ≤ 10,000.** Query, read `totalResults`, and if it's over 10k, halve the rank range and re-check. Keep halving until each bucket fits, then page it out.

Good news — your token estimate survives this. Cost is 10/request + 1 per 100 ASINs either way, so `ceil(20.89M/10000)*10 + ceil(20.89M/100)` ≈ 230K tokens is still roughly right. It's the mechanism that's broken, not the budget.

```plaintext
    while (queue.length && batch.length < BATCH) {
      const [cid, depth] = queue.shift();
      if (nodes.has(cid)) continue;
      batch.push([cid, depth]);

    if (found === null) break;
```

```plaintext
 *
 * Replaces fixed rank windows, which reach only 3.5% of the catalogue.
 * trackingSince is present on 100% of products and is single-valued, so
 * buckets never overlap and never need deduplication.
 *
 * Algorithm:
 *   1. Probe a trackingSince range with perPage=50 (~11 tokens) to read totalResults.
 *   2. If it fits under the cap, harvest the whole bucket in ONE request
 *      (page 0 allows perPage up to 10,000).
 *   3. If not, halve the range and push both halves back on the stack.

async function run() {
  while (stack.length && !shouldStop()) {
    const [lo, hi] = stack.pop();

    // Probe cheaply for the count.
    const probe = await query(lo, hi, PROBE_PER_PAGE);
    if (!probe) break;
    probes++;
    if (probe.failed) continue;

    const total = probe.total || 0;

    if (total === 0) {
      bucketsDone++;
      continue;
    }

    if (total <= BUCKET_TARGET) {
      // Fits. Harvest the whole bucket in one request (page 0 allows perPage 10,000).
      const harvest = await query(lo, hi, Math.min(HARD_CAP, Math.max(50, total)));
      if (!harvest) break;
      harvests++;
      if (harvest.failed) continue;

      if (harvest.asins.length) {
        asinStream.write(harvest.asins.join("\n") + "\n");
        asinsWritten += harvest.asins.length;
      }

      // Counts drift between calls; if we hit the cap with more outstanding, split.
      if (harvest.total > harvest.asins.length && harvest.asins.length >= HARD_CAP) {
        const mid = Math.floor((lo + hi) / 2);
        if (hi > lo) stack.push([lo, mid], [mid + 1, hi]);
      }

      bucketsDone++;
      report(lo, hi, total, harvest.asins.length);
      checkpoint();
      continue;
    }

    // Too big. Halve it.
    if (hi <= lo) {
      // A single trackingSince minute holding more than the cap. Take what we
      // can and record the shortfall rather than looping forever.
      const harvest = await query(lo, hi, HARD_CAP);
      if (harvest && !harvest.failed && harvest.asins.length) {
        asinStream.write(harvest.asins.join("\n") + "\n");
        asinsWritten += harvest.asins.length;
        harvests++;
      }
      unresolvable.push({ minute: lo, total, retrieved: HARD_CAP, lost: total - HARD_CAP });
      console.log(`  [${elapsed()}] ! minute ${lo} holds ${fmt(total)}; ${fmt(total - HARD_CAP)} unreachable`);
      bucketsDone++;
      checkpoint();
      continue;
    }

    const mid = Math.floor((lo + hi) / 2);
    stack.push([lo, mid], [mid + 1, hi]);
  }
}
```

## Same ASIN twice in the file — almost never, but I left a bug

`trackingSince` is a single value per product, and the buckets are disjoint ranges, so a book can only ever fall into one bucket. That's the whole reason I chose that axis — no deduplication step, no 42-million-string Set eating your RAM.

But there are two ways duplicates can sneak in, and one of them is my fault:

**My drift-resplit branch is wrong.** Look at what happens when a harvest hits the 10,000 cap with results still outstanding: the script writes those 10,000 ASINs to disk, _then_ pushes both halves back on the stack. When those halves get harvested, they re-emit the same ASINs. Straightforward fix — don't write when you're about to resplit:

```js
if (harvest.total > harvest.asins.length && harvest.asins.length >= HARD_CAP) {
  const mid = Math.floor((lo + hi) / 2);
  if (hi > lo) { stack.push([lo, mid], [mid + 1, hi]); bucketsDone++; continue; }
}
// only write if we're NOT resplitting
if (harvest.asins.length) { asinStream.write(...); asinsWritten += ...; }
```

**Crash between write and checkpoint.** The checkpoint saves after each bucket. If the process dies in the gap, resume redoes that bucket and duplicates up to 9,500 lines. Rare, bounded, harmless.

Either way, check it in one command:

```bash
sort discovered_asins.txt | uniq -d | wc -l
```

Zero is expected. Deduping is `sort -u` and costs nothing, so just do it before the metadata pass regardless — every duplicate ASIN is a wasted token.

## Same _book_ under different ASINs — yes, a lot

This is the real issue, and no filter fixes it.

Amazon gives a separate ASIN to every printing. One novel might legitimately appear as:

- Paperback (its own ISBN)
- Hardcover (its own ISBN)
- Mass market paperback (its own ISBN)
- The 2019 reprint, the 2023 reprint
- The Indian edition and the imported US edition
- A listing some seller created badly instead of matching to the existing one

Every one of those is a distinct ASIN with a distinct ISBN, and all of them are genuinely in the catalogue. So **15.8 million ASINs is meaningfully fewer than 15.8 million books**, and I won't guess a ratio — it varies enormously by category and I'd just be making it up.

One thing does help: `productType: 0` already excludes VARIATION_PARENT (type 5), so you're not getting phantom parent listings on top of their children.

Converting ISBN-10 to ISBN-13 won't help either, by the way. That conversion is deterministic — same book, same answer, every time — so it can't merge anything that wasn't already identical.

## How to collapse editions, if you need to

Depends what you're building. If it's a price dataset, **don't** — you _want_ each edition separately, because they're priced differently and that's the point.

If you want a list of distinct works, the clean route is Open Library. It explicitly models editions-versus-works and gives every work a stable key, so you look up each ISBN, take the work ID, and group by that. It's free, it's the mapping you'd otherwise have to invent, and it handles the hard cases (same book, different title in a different market) that title-matching gets wrong.

The rough alternative is normalising title + first author and fuzzy-matching. Fast to write, but it'll merge things it shouldn't and split things it should merge.

Worth deciding now, because it changes nothing about the collection run — you'd do the grouping afterwards on data you already have.
